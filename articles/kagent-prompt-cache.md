## はじめに

前回の記事ではsystemMessageを8万文字から400文字に圧縮し、1リクエストあたりのトークン消費を16万→8万に削減しました。

https://zenn.dev/your-username/articles/kagent-context-engineering

しかし8万トークンはまだ大きい。内訳を見るとこうなっています。

```
残っているコスト内訳
├── ツール定義（BigQuery MCP）: ~40,000トークン  ← 毎回変わらない
├── チャット履歴:              ~30,000トークン  ← ターンごとに増える
├── 今回の質問:                 ~5,000トークン
└── systemMessage:               ~400トークン
```

ツール定義40,000トークンは毎回全く同じ内容を送っているのに、毎回フル課金されています。

これをコードを一行も書かずに解決できる仕組みがGeminiのプロンプトキャッシュです。ただし「ただ使えば効く」ものではなく、コンテキストの設計が前提になります。

:::message
本記事は前回の構成（GKE Autopilot + Kagent v0.8.6 + Gemini 2.5 Flash）を前提にしています。
:::

## キャッシュの基礎

### キャッシュとは何か

「処理コストが高いデータを、より速くアクセスできる場所に一時保存しておく仕組み」です。

コンピュータのメモリには速度と容量のトレードオフがあります。

```
          速い・小さい・高価
               ▲
               │  CPU レジスタ    ← 演算中の値（数十バイト）
               │  L1/L2 キャッシュ ← 直近の命令・データ（数MB）
               │  RAM（主記憶）    ← 実行中のプログラム（数GB）
               │  SSD / HDD       ← ファイル・DB（数TB）
               ▼
          遅い・大きい・安価
```

CPUがRAMのデータを使うたびにHDDから読んでいたら遅すぎる。だから「直近使ったデータをRAMに置いておく」というのがキャッシュの原点です。

### Webサーバでのキャッシュ

Webの世界でも同じ考え方が使われています。ユーザーのリクエストに対して毎回DBにアクセスしていると遅い。だから途中に高速なキャッシュ層を挟みます。

```
                      ユーザーのリクエスト
                              │
                              ▼
                    ┌─────────────────┐
                    │   CDN / Edge    │  ← 静的コンテンツ（画像・JS）
                    │   キャッシュ     │    世界中のサーバに分散して保持
                    └────────┬────────┘
                             │ キャッシュミス時のみ通過
                             ▼
                    ┌─────────────────┐
                    │  Webサーバ /    │
                    │  リバースProxy  │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  Redis / Memcached│ ← アプリキャッシュ
                    │  アプリキャッシュ │   DBクエリ結果などを保持
                    └────────┬────────┘
                             │ キャッシュミス時のみ通過
                             ▼
                    ┌─────────────────┐
                    │    DB / API     │  ← 本来のデータソース
                    └─────────────────┘
```

キャッシュのロジックはどの層でも同じです。

```
リクエストが来る
    │
    ▼
キャッシュを確認
    │
    ├─ ヒット → キャッシュから返す（速い・安い）
    │
    └─ ミス  → 本来のソースから取得
                    │
                    ├─ 結果をキャッシュに保存
                    │
                    └─ レスポンスを返す（遅い・高い）
```

### キャッシュが機能する条件

どの層のキャッシュにも共通する前提があります。

```
前提1: 同じリクエストが繰り返される
       1回しか来ないリクエストはキャッシュしても意味がない

前提2: レスポンスが変わらない（または変わっても許容できる）
       「今日の日付」をキャッシュすると翌日に古い値を返す

前提3: キャッシュを保持するコストより節約できるコストが大きい
       1秒に1回しか呼ばれないAPIをキャッシュしてもほぼ効果なし
```

これがLLMのプロンプトキャッシュでも全く同じように問題になります。

## 前提：プロンプトキャッシュとは

LLMはリクエストを受け取るたびに、送ったトークンを先頭から順番に処理します。キャッシュなしだと、毎回同じ内容（ツール定義など）を繰り返し処理し続けます。

```
キャッシュなし（毎回全トークンをフル処理）

1ターン目:
 ┌─────────────────────────────────────┬────────────┐
 │  systemMsg + ツール定義   (40,400)  │  質問 (5k) │
 │  ← 毎回同じ内容 →                  │            │
 └─────────────────────────────────────┴────────────┘
   全部LLMが処理 → 全部フル課金 💸

2ターン目:
 ┌─────────────────────────────────────┬─────────────────┐
 │  systemMsg + ツール定義   (40,400)  │  履歴+質問 (15k)│
 │  ← 前回と全く同じ内容 →            │                 │
 └─────────────────────────────────────┴─────────────────┘
   また全部処理 → またフル課金 💸
```

プロンプトキャッシュは「先頭部分が前回と同じなら、その処理をスキップする」仕組みです。

```
キャッシュあり（先頭一致部分はスキップ）

1ターン目:
 ┌─────────────────────────────────────┬────────────┐
 │  systemMsg + ツール定義   (40,400)  │  質問 (5k) │
 └─────────────────────────────────────┴────────────┘
   LLMが処理 → フル課金                  フル課金
                      ↓
               💾 キャッシュに保存

2ターン目:
 ┌─────────────────────────────────────┬─────────────────┐
 │  systemMsg + ツール定義   (40,400)  │  履歴+質問 (15k)│
 └─────────────────────────────────────┴─────────────────┘
   ✅ キャッシュヒット → 75%オフ 🎉        フル課金
```

キャッシュが効く条件はシンプルです。

```
条件1: 先頭から連続して一致していること
       途中からの一致は無効

条件2: 共通部分が 1,024 トークン以上あること
       systemMessageだけ（400トークン）では届かないが
       ツール定義を加えると 40,400 トークンで余裕でクリア
```

この2点を意識したコンテキスト設計が、本記事のテーマです。

## キャッシュの構造：2つのレイヤー

「キャッシュを入れる」と一口に言っても、どこにキャッシュするかによって解決できる問題が全く違います。まずこの構造を整理しておきます。

```
ユーザーの質問
    ↓
Kagent Controller
    ↓ ① アプリサイドキャッシュ（Layer 2）
ツール定義フェッチ（MCP Serverから）
    ↓
コンテキスト組み立て
    ↓
Gemini API
    ↓ ② LLMサイドキャッシュ（Layer 1）
トークン処理
    ↓
回答
```

### Layer 1：LLMサイドキャッシュ（Geminiが持つ）

Gemini APIが自動的に行うキャッシュです。リクエストの先頭部分が前回と一致していれば、その部分のトークン処理をスキップします。

- 解決する問題：LLM APIの課金コスト
- 実装コスト：ゼロ（自動）
- 効果：キャッシュヒット部分が75%オフ

### Layer 2：アプリサイドキャッシュ（自分で実装する）

Kagentがコンテキストを組み立てる前の段階、MCPサーバーからツール定義を取得する処理をキャッシュします。

- 解決する問題：MCPサーバーへの往復レイテンシ・フェッチ処理の負荷
- 実装コスト：自分で組む必要がある
- 効果：レスポンス速度の改善（トークン課金は減らない）

### Layer 2の実装選択肢

アプリサイドキャッシュをどこに置くかは構成によって変わります。

① In-pod（インメモリ）

```
[Agent Pod]
├── Kagent Controller
└── 🗄️ インメモリキャッシュ
      起動時にMCPからツール定義を取得し、メモリに保持
```

| | 内容 |
|---|---|
| メリット | レイテンシ最小・追加インフラ不要・シンプル |
| デメリット | Pod再起動で消える・複数レプリカ間で共有できない |
| 向いている構成 | レプリカ数1・Pod再起動が少ない環境 |

② Redis（外部キャッシュ）

```
[Agent Pod A]  [Agent Pod B]  [Agent Pod C]
      ↓               ↓               ↓
         [Redis / Cloud Memorystore]
              全レプリカで共有
```

| | 内容 |
|---|---|
| メリット | 複数レプリカ間で共有・Pod再起動後も残る・TTL管理が柔軟 |
| デメリット | インフラが増える（GKEならMemorystoreの費用）・ネットワーク遅延が加わる |
| 向いている構成 | レプリカ数2以上・高可用性が求められる環境 |

### どちらを選ぶか

ツール定義のキャッシュ目的であれば、まず考慮すべき点はレプリカ数です。

```
レプリカ数 = 1  →  In-podで十分
レプリカ数 > 1  →  Redisを検討
```

ただし、ツール定義のキャッシュはLayer 2（アプリサイド）で行っても課金コストには直接影響しません。課金を下げたいのであれば、Layer 1（LLMサイド）を正しく機能させる設計が先決です。

本記事ではLayer 1に集中します。Layer 2はレイテンシ改善が目的になったタイミングで検討してください。

## Gemini implicit cachingの仕組み

Gemini 2.5 FlashはAPIレベルでimplicit caching（自動キャッシュ）を提供しています。

仕組みはシンプルです。リクエストの先頭部分（プレフィックス）が前回のリクエストと一致していれば、その部分のトークン処理をスキップしてキャッシュヒット扱いにします。キャッシュされたトークンは通常の約75%オフで課金されます。

```
1ターン目（初回 → キャッシュなし）
┌─────────────────────────────────────┐
│ systemMessage       400トークン     │ フル処理・フル課金
│ ツール定義       40,000トークン     │ フル処理・フル課金
│ チャット履歴          0トークン     │
│ 今回の質問        5,000トークン     │
└─────────────────────────────────────┘

2ターン目（プレフィックスが一致 → キャッシュヒット）
┌─────────────────────────────────────┐
│ systemMessage       400トークン     │ ✅ キャッシュヒット → 75%オフ
│ ツール定義       40,000トークン     │ ✅ キャッシュヒット → 75%オフ
├─────────────────────────────────────┤ ← ここまでが一致
│ チャット履歴     10,000トークン     │ フル課金（前回から追加された）
│ 今回の質問        5,000トークン     │ フル課金
└─────────────────────────────────────┘
```

### キャッシュが効く2つの条件

条件1：先頭から連続して一致していること

キャッシュはプレフィックスの一致判定です。途中から一致しても意味がありません。

```
✅ 先頭から一致 → キャッシュヒット
[systemMessage][ツール定義][履歴（新しい）][質問（新しい）]
 ↑ここから一致─────────↑ここまでヒット

❌ 途中から一致 → キャッシュミス
[systemMessage][履歴（変わった）][ツール定義][質問]
 ↑ここで変わる → 以降は全てミス
```

条件2：1,024トークン以上の共通プレフィックスであること

小さすぎるプレフィックスはキャッシュの対象外です。systemMessageだけ（400トークン）では届きませんが、ツール定義を加えると40,400トークンになり、条件を余裕でクリアします。

## キモ：コンテキストの順序設計

implicit cachingを機能させる上で最も重要なのがコンテキストをどの順番で組み立てるかです。

### 正しい順序

```
[固定] systemMessage → [固定] ツール定義 → [変動] チャット履歴 → [変動] 質問
```

変わらない情報を先頭に集め、変わる情報を末尾に置く。この順序が保たれていれば、毎ターンsystemMessageとツール定義のキャッシュが効き続けます。

### 順序が崩れるとどうなるか

```
❌ NG例：履歴がツール定義より前に来ている
[systemMessage] → [チャット履歴] → [ツール定義] → [質問]
                   ↑ここで前回と変わる
                     → 以降のツール定義もキャッシュミスになる
```

ターンを重ねるたびに履歴が変化するため、その後ろにあるツール定義は毎回フル課金になります。

## キャッシュが壊れやすいパターン

順序が正しくても、キャッシュが無効化されるケースがあります。

### パターン1：systemMessageに動的な値を入れる

```yaml
# ❌ キャッシュが毎日壊れる
systemMessage: |
  あなたはKubernetesのコスト最適化エージェントです。
  本日の日付: 2026/05/24  ← 日付が変わるたびにミス
  ...

# ✅ 固定値のみ
systemMessage: |
  あなたはKubernetesのコスト最適化エージェントです。
  ...
```

### パターン2：ツール定義の内容が変わる

MCPサーバーのバージョンアップなどでツールスキーマが変わると、その時点でキャッシュが無効化されます。意図しないバージョンアップには注意が必要です。

### パターン3：TTLを超える

Geminiのimplicit cachingのTTLは非公開ですが、リクエスト間隔が数分を超えるとキャッシュが切れる場合があります。バッチ的な使い方（数十分おきに1リクエスト）はキャッシュの恩恵を受けにくいです。

## キャッシュが効いているか確認する

Vertex AIコンソールの「Use」タブからトークンの内訳を確認できます。

```
[Vertex AI コンソール → モデルの使用状況]
Total input tokens:       45,400
  Cached tokens:          40,400  ← ここが0でないかチェック
  Non-cached tokens:       5,000
Output tokens:             5,000
```

`Cached tokens` が `systemMessage + ツール定義` のサイズ（今回は約40,400トークン）に近い値であれば、正しくキャッシュが効いています。

APIレスポンスのメタデータからも確認できます。

```python
response = client.models.generate_content(...)

usage = response.usage_metadata
print(f"Total input:  {usage.prompt_token_count}")
print(f"Cached:       {usage.cached_content_token_count}")  # ← ここ
print(f"Output:       {usage.candidates_token_count}")
```

## コスト試算

Gemini 2.5 Flashの料金（参考）で計算します。

```
通常の入力トークン:  $0.075 / 1Mトークン
キャッシュヒット:    $0.01875 / 1Mトークン（75%オフ）
```

| | Before（キャッシュなし） | After（キャッシュあり） |
|---|---|---|
| 課金対象トークン/req | 75,000 | ~5,000（履歴・質問のみ） |
| 100req/日のコスト | $0.56/日 | $0.14/日 |
| 月額換算 | ~$17/月 | ~$4/月 |

ツール定義のキャッシュが効くだけで、2ターン目以降の課金が大幅に下がります。

## 前回記事との関係

コンテキストエンジニアリングとプロンプトキャッシュは同じ目標に向かう両輪です。

```
コンテキストエンジニアリング（前回）
└── systemMessageを小さくする
    └── 「変わらない部分」を最小化

プロンプトキャッシュ（今回）
└── 「変わらない部分」の課金を75%オフにする
    └── 前回の最適化があってこそ効果が出る
```

前回でsystemMessageが8万文字のままだったら、動的な情報（日付など）が混入している可能性が高く、キャッシュは機能しなかったでしょう。まずコンテキストを整理してから、キャッシュを効かせる——という順序が重要です。

## まとめ

| フェーズ | 入力トークン/req | 実質課金トークン/req |
|---------|----------------|-------------------|
| 最初（素の状態） | 155,000 | 155,000 |
| 前回（context engineering） | 75,000 | 75,000 |
| 今回（+implicit caching） | 75,000 | ~5,000 |

トークン数は変わっていないのに、実質の課金が大幅に下がります。

implicit cachingを正しく機能させるポイントをまとめます。

- 固定情報を先頭に、変動情報を末尾に置く（順序が全て）
- systemMessageに動的な値を混ぜない（前回記事の前提が活きる）
- Cached tokensの数値を見て効いているか確認する
- コードの変更は不要。設計だけで効果が出る
